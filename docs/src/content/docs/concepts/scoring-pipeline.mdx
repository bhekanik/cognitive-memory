## Overview

When you call `search()`, the query goes through a multi-stage pipeline that combines vector similarity, temporal decay, associative expansion, and retrieval boosting to produce a ranked list of memories. `retrieve()` is a compatibility wrapper over the same pipeline.

## The six stages

### Stage 1: Vector similarity search

The query text is embedded, and the hot store is searched for the top candidates by cosine similarity:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    candidates = await self.adapter.search_similar(
        query_embedding,
        top_k=top_k * rerank_factor,
        include_superseded=deep_recall,
        include_cold=deep_recall,
        include_stubs=False,
    )
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    const candidates = await this.adapter.vectorSearch(queryEmbedding, {
      userId: this.config.userId,
      limit: limit * rerankFactor,
      includeSuperseded: deepRecall,
      includeCold: deepRecall,
      includeStubs: false,
    });
    ```
  </TabItem>
</Tabs>

When reranking is enabled, the search can request `top_k * rerank_factor` candidates before slicing back to the requested `top_k`.

### Stage 1b: Lexical/BM25 search (v6, when hybrid enabled)

When `hybrid_search` / `hybridSearch` is enabled, a parallel BM25 lexical search runs against the adapter's `search_lexical` / `searchLexical` method:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    lexical_candidates = await self.adapter.search_lexical(
        query_text, top_k=k_sparse,
    )
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    const lexicalCandidates = await this.adapter.searchLexical(queryText, {
      userId: this.config.userId,
      limit: kSparse,
    });
    ```
  </TabItem>
</Tabs>

Results are unioned with the dense candidates from Stage 1. Duplicate memories (found by both paths) are kept once. This ensures exact keyword matches surface even when they aren't the closest vectors.

### Stage 2: Retention-weighted scoring

Each candidate is scored with the R^alpha formula:

```
combined_score = sim(m,q) * R(m)^alpha
```

Where alpha = 0.3 (configurable). This softens the decay penalty so faded but relevant memories can still surface.

For superseded memories in deep recall mode, an additional penalty is applied:

```
combined_score *= deep_recall_penalty  # default: 0.5
```

Candidates are sorted by combined score. If reranking is disabled, the requested top-k become the direct results. If reranking is enabled, the expanded pool continues to the rerank stage first.

### Stage 2b: Validity filtering (v6)

Candidates with semantic type `plan` or `transient_state` whose validity window has expired are removed from the candidate pool, unless transient filtering is disabled or deep recall is active with `include_expired_in_deep_recall` / `includeExpiredInDeepRecall` enabled. See [Deep Recall — Validity-based filtering](/cognitive-memory/concepts/deep-recall/#validity-based-filtering) for details.

### Stage 2c: LLM reranking (optional)

When `rerank_enabled` / `rerankEnabled` is `True` and an LLM provider is available, the engine retrieves an expanded candidate pool (`top_k * rerank_factor`, with `k_rerank` as a floor), sends those candidates to the LLM, then returns the requested `top_k`. This can improve precision for ambiguous or nuanced queries at the cost of additional latency and token usage. The model used defaults to the configured extraction model unless `rerank_model` / `rerankModel` is set explicitly.

### Stage 3: Associative expansion

For each direct result, the engine looks up its association graph:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    for result in direct_results:
        associated = self.get_associated_memories(result.memory, now)
        for assoc_mem, assoc_weight in associated:
            # Score: sim * R^alpha * association_weight
            ...
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    for (const result of directResults) {
      const associated = await this.getAssociatedMemories(result.memory, now);
      for (const { memory, weight } of associated) {
        // Score: sim * R^alpha * association weight
        // ...
      }
    }
    ```
  </TabItem>
</Tabs>

Associated memories are scored by their own similarity and retention, multiplied by the association weight. Only associations with weight >= 0.3 (after decay) are activated.

This stage can pull in memories from cold storage — if a cold memory is linked to a direct result, it's scored and included.

### Stage 3b: Graph expansion + bridge discovery (v6)

After associative expansion, the engine can perform a second hop through the association graph looking for **bridge memories** — nodes that connect otherwise unrelated clusters. Bridge memories are scored and included if they exceed a minimum relevance threshold, enabling cross-topic recall.

### Stage 4: Retrieval boosting

All memories in the result set receive retrieval boosts:

- **Direct results:** `stability += 0.1 * spaced_rep_factor`
- **Associative results:** `stability += 0.03 * spaced_rep_factor`

Both types also get: `access_count += 1`, `last_accessed_at = now`, session ID added.

Cold memories that were retrieved via associations are migrated back to hot storage.

### Stage 5: Core promotion check

Every memory in the result set is checked against the core promotion criteria:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    for result in all_results:
        self.check_core_promotion(result.memory)
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    for (const result of allResults) {
      await this.checkCorePromotion(result.memory);
    }
    ```
  </TabItem>
</Tabs>

If a memory has access_count >= 10, stability >= 0.85, and sessions >= 3, it's promoted to core.

### Stage 6: Co-retrieval strengthening

All pairs of direct results have their association links strengthened:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    for i in range(len(direct_mems)):
        for j in range(i + 1, len(direct_mems)):
            self.strengthen_association(direct_mems[i], direct_mems[j], now)
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    for (let i = 0; i < directMemories.length; i++) {
      for (let j = i + 1; j < directMemories.length; j++) {
        await this.strengthenAssociation(directMemories[i], directMemories[j], now);
      }
    }
    ```
  </TabItem>
</Tabs>

This creates new associations (or strengthens existing ones) between memories that co-occur in search results. Over time, this builds a rich associative graph that reflects query patterns.

## Final merge and return

Direct and associative results are merged, deduplicated by memory ID, sorted by combined score, and truncated to top-k:

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    all_results = direct_results + associative_results
    all_results.sort(key=lambda x: x.combined_score, reverse=True)
    return all_results[:top_k]
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    const allResults = [...directResults, ...associativeResults]
      .sort((a, b) => b.combinedScore - a.combinedScore)
      .slice(0, limit);

    return allResults;
    ```
  </TabItem>
</Tabs>

## What the caller receives (v6 breaking change)

In v6, `search()` returns a **`SearchResponse`** wrapper instead of a bare list. This is a breaking change from v5.

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    @dataclass
    class SearchResponse:
        results: list[SearchResult]  # ranked results (same as before)
        trace: SearchTrace           # pipeline instrumentation

    @dataclass
    class SearchResult:
        memory: Memory
        relevance_score: float
        retention_score: float
        combined_score: float
        is_associative: bool
        via_deep_recall: bool

    @dataclass
    class SearchTrace:
        stages: dict[str, StageTrace]
        total_ms: float
        total_tokens: int    # sum of all prompt + completion tokens across stages

    @dataclass
    class StageTrace:
        name: str            # e.g. "vector_search", "bm25_search", "validity_filter", "rerank"
        candidate_count: int # candidates entering this stage
        survivor_count: int  # candidates leaving this stage
        duration_ms: float
        prompt_tokens: int   # LLM prompt tokens used (0 for non-LLM stages)
        completion_tokens: int # LLM completion tokens used (0 for non-LLM stages)
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    interface SearchResponse {
        results: SearchResult[];
        evidenceChains: string[][];
        trace?: SearchTrace;
    }

    interface SearchResult {
        memory: Memory;
        relevanceScore: number;
        retentionScore: number;
        combinedScore: number;
        isAssociative: boolean;
        viaDeepRecall: boolean;
    }

    interface SearchTrace {
        stages: Record<string, StageTrace>;
        totalWallMs: number;
        totalTokens: number;       // sum of all prompt + completion tokens across stages
    }

    interface StageTrace {
        name: string;
        candidateCount: number;
        wallMs: number;
        promptTokens?: number;      // LLM prompt tokens used (0 for non-LLM stages)
        completionTokens?: number;  // LLM completion tokens used (0 for non-LLM stages)
    }
    ```
  </TabItem>
</Tabs>

### Trace / instrumentation

The `SearchTrace` attached to every response provides full visibility into the pipeline. Each `StageTrace` records the stage name, how many candidates entered and survived, and wall-clock time. This is useful for debugging relevance issues, tuning `top_k` multipliers, and understanding why specific memories did or did not appear.

<Tabs syncKey="lang">
  <TabItem label="Python">
    ```python
    response = await mem.search("coffee preferences")
    for name, stage in response.trace.stages.items():
        print(f"{name}: {stage.candidate_count} candidates ({stage.wall_ms:.1f}ms)")
    ```
  </TabItem>
  <TabItem label="TypeScript">
    ```typescript
    const response = await mem.search({
      query: "coffee preferences",
      trace: true,
    });

    for (const [name, stage] of Object.entries(response.trace?.stages ?? {})) {
      console.log(`${name}: ${stage.candidateCount} candidates (${stage.wallMs.toFixed(1)}ms)`);
    }
    ```
  </TabItem>
</Tabs>

## Pipeline summary

```
Query text
    |
    v
Embed query
    |
    v
Stage 1:  Vector search (normal: hot only; deep recall: cold + superseded too)
Stage 1b: BM25 lexical search (if hybrid enabled)
    |
    v
Stage 2:  Score by sim * R^alpha
Stage 2b: Validity filtering (expired plan/transient exclusion)
Stage 2c: LLM reranking (if enabled; top_k * rerank_factor candidates -> top_k)
    |
    v
Stage 3:  Expand via associations (cold store too)
Stage 3b: Graph expansion + bridge discovery
    |
    v
Stage 4: Apply direct/associative boosts
    |
    v
Stage 5: Check core promotions
    |
    v
Stage 6: Strengthen co-retrieved associations
    |
    v
Merge, sort, return SearchResponse (results + trace)
```

Every search actively reshapes the memory system: boosting stabilities, creating/strengthening associations, promoting cores, and reactivating cold memories. The system gets smarter with every query.
